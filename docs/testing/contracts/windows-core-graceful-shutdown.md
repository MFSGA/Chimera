# Windows core graceful shutdown contract

- **Contract ID:** `windows-core-graceful-shutdown`
- **Case:** A graceful stop sends Ctrl+Break only to the target core process group; a sibling sharing the test runner's console remains alive.
- **Regression:** The ref core's `CREATE_NO_WINDOW` setting conflicts with helper `AttachConsole(pid)`, while `CTRL_C_EVENT` with process group `0` broadcasts to other processes on the console. This test detects the sibling broadcast; it does not exercise the old no-console attach path.
- **Boundary / suite:** Rust Windows process integration test in the `chimera-utils` runtime submodule. The test uses real Windows console process groups and Job Objects; it is not a fixture-only claim. The current root CI does not run this submodule test.
- **Runtime conditions:** Windows; one test process; test child executable built from `tests/helpers/test_child.rs`; no network, core binary, TUN, or host proxy required. The test reuses the console available to the test runner when one exists.
- **Real dependencies:** Shared `chimera-utils` process engine, ProcessKit Windows Job Object, test-runner console, target and sibling child processes, shutdown helper entry point, filesystem marker in a unique temporary directory.
- **Mocks / bypasses:** None for process creation, console signaling, or containment. The test child registers Tokio's real Windows `ctrl_break()` listener and writes a marker only after receiving `CTRL_BREAK_EVENT`.
- **Initial state:** Start two live child processes through `Command::spawn`; each prints `ready`, belongs to a Job Object, and has its own process group on the same host console. The test verifies each readiness event before stopping anything.
- **Operation:** Call `graceful_kill()` once on the first child's `ProcessHandle`.
- **Authoritative result:** The first child exits successfully and writes `ctrl-break-received` to its unique marker. A 250 ms bounded observation of the sibling's wait must time out, and the sibling's marker must remain absent.
- **UI / persistence:** Not applicable; this contract covers process lifecycle only.
- **Failure path:** Start a child with a nonexistent helper path and a five-second grace period. `graceful_kill()` must return in under two seconds, the child must be reaped with a nonzero exit, and containment must be `JobObject`; this proves helper startup failure falls through to hard tree termination instead of waiting out the grace period.
- **Wait budget:** Five seconds for each child readiness; two seconds for the targeted graceful stop; 250 ms sibling non-delivery observation; two seconds for missing-helper fallback. The CI job should leave additional build and cleanup time.
- **Diagnostics:** Rust assertion output and test runner output only. Markers are created inside the test-owned temporary directory and removed when it is dropped.
- **Resources / cleanup:** The test owns both process handles, event receivers, and its temporary directory. It explicitly kills the sibling on success; handle drop/Job Object close reaps children on assertion failure or cancellation.
- **Regression sensitivity:** A broadcast `CTRL_C_EVENT` or broadly targeted control event makes the sibling exit/write its marker, failing the sibling assertions. This test does not cover production host hidden-console allocation (`AllocConsoleWithOptions` or the older `AllocConsole`/hide fallback).
- **Applicable rules:** T01 (falsifiable behavior), T02 (integration boundary), T07 (owned process and temporary data), T09 (helper failure and fallback invariant), T10 (cleanup). Network and UI rules do not apply.
- **Current evidence:** macOS `cargo test` passes the `chimera-utils` 30-test suite and 1 doctest but excludes this `cfg(windows)` test. `cargo check --tests --target x86_64-pc-windows-gnu -p chimera-utils --features process` compiles the Windows helper and integration test. Running the control-event assertions is still required; the macOS host has no MinGW compiler, and the connected Windows workspace could not be opened during this task. Actual core behavior on `CTRL_BREAK_EVENT` also remains to be confirmed on Windows; Job Object termination remains the bounded fallback.
