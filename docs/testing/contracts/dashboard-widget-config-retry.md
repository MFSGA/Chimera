# Dashboard widget configuration retry contract

- Contract ID: `dashboard-widget-config-retry`.
- Boundary: desktop UI E2E through the Dashboard, Tauri KV IPC and persistent storage. The test injects a bounded IPC failure to exercise the application's recovery path.
- Suite and execution: `dashboard-main-layout.e2e.ts`, registered in `main` and therefore executed by the Windows `hermetic` PR suite.
- Initial state: open the main Dashboard, read the existing `dashboard-widget-configs` value, and retain it for cleanup.
- Failure operation: in one WebDriver execution, clear any prior test-owned interceptor state and replace the main WebView's Tauri `invoke` function; verify the wrapper remains installed after SPA route setup, and fail Dashboard `get_storage_item` requests until the intercepted-call counter advances and the `load-error` state is observed. Release the injected failure, exit edit mode and use the visible Retry control; the retry must succeed. Route setup preserves the document so the test can prove the targeted UI read actually reached the injected boundary.
- Save failure: inject one `set_storage_item` failure, change the Traffic Down unit through the visible configuration menu, assert the error state and verify the stored backend value remains unchanged. Retry from the visible control and verify both the rendered value and stored value change.
- Unsupported-version recovery: write a version-2 configuration while the Dashboard is open and confirm the storage event exposes the load-error state. Verify setting and reset controls are disabled and the exact raw version-2 value is preserved. Refresh and verify an initial read of that same value also blocks edits without rewriting it; restore a supported version before continuing.
- Persistence: after observing the live UI and backend value, refresh the page and verify the selected unit is rendered again. Restore the original stored string and verify it before final refresh.
- Driver boundary: the vendored Tauri WebDriver synthesizes an untrusted `pointerdown` on pointer presses, then the corresponding mouse event; after a matched right-button press/release it emits a bubbling, cancellable `contextmenu` event. The `pointerdown` is required because the shared context-menu provider records the target in a document capture listener before resolving registered Dashboard menu items. This verifies the app's synthetic event handling and following UI action; it does not prove trusted native mouse input or a complete PointerEvent sequence. Recheck this boundary when upgrading the vendored driver.
- Diagnostics and cleanup: on failure, save screenshot, page source and error under the configured E2E artifact directory before cleanup. Stop and restore the test-owned Tauri invoke interceptor, wait for a pending setting write when possible, then attempt the original KV write, readback, refresh, route recovery and final readback even if an earlier cleanup step fails. Aggregate cleanup errors and preserve the primary test error if both fail.
- Recovery coverage: a failure to read must expose Retry; a failed write must preserve the old backend value; an unsupported version from an event or initial read must block edits and preserve the exact stored value; a successful retry must converge in the current UI and storage; refresh must reload the persisted value.
