# Dashboard widget configuration retry contract

- Contract ID: `dashboard-widget-config-retry`.
- Boundary: desktop UI E2E through the Dashboard, Tauri KV IPC and persistent storage. The E2E-only Rust fixture injects a bounded failure at the real storage command boundary to exercise the application's recovery path.
- Suite and execution: `dashboard-main-layout.e2e.ts`, registered in `main` and therefore executed by the Windows `hermetic` PR suite.
- Deterministic presentation setup: save the current theme, set `light` through `patch_verge_config`, verify the class on the actual `#root` theme target, and restore the original mode in suite cleanup. The spec does not change the app language. UI controls are located through stable `data-slot` / `data-config-field` attributes rather than translated labels.
- Initial state: open the main Dashboard, read the existing `dashboard-widget-configs` value, and retain it for cleanup.
- Failure operation: use the `e2e` feature's app-level `e2e_arm_widget_storage_failure` command for `get_storage_item`, then navigate to Dashboard and verify through `e2e_widget_storage_failure_status` that the real command boundary observed the read. Keep the failure armed until the UI displays `load-error`; clear the fixture, exit edit mode and use the visible Retry control. The retry must succeed through the original Tauri invoke path.
- Save failure: arm one `set_storage_item` failure, change the Traffic Down unit through the visible configuration menu, assert the error state and verify the fixture reports exactly one real command failure while the stored backend value remains unchanged. Retry from the visible control and verify both the rendered value and stored value change.
- Unsupported-version recovery: write a version-2 configuration while the Dashboard is open and confirm the storage event exposes the load-error state. Open the Traffic widget popover only when its trigger reports `aria-expanded="false"`; after clicking, wait for `aria-expanded="true"` before checking that both the speed-unit and Reset controls are visible. On timeout, include trigger expansion, Popover field mounting, both controls' visibility/disabled state, and save status so a closed portal can be distinguished from a disabled control. Verify setting and reset controls are disabled and the exact raw version-2 value is preserved. Refresh and verify an initial read of that same value also blocks edits without rewriting it; restore a supported version before continuing.
- Persistence: after observing the live UI and backend value, refresh the page and verify the selected unit is rendered again. Reopen the widget config popover before checking control availability after clicking Retry in the edit toolbar, since that control is outside the popover and the click closes it. Restore the original stored string and verify it before final refresh.
- Driver boundary: the vendored Tauri WebDriver synthesizes an untrusted `pointerdown` on pointer presses, then the corresponding mouse event; after a matched right-button press/release it emits a bubbling, cancellable `contextmenu` event. The `pointerdown` is required because the shared context-menu provider records the target in a document capture listener before resolving registered Dashboard menu items. This verifies the app's synthetic event handling and following UI action; it does not prove trusted native mouse input or a complete PointerEvent sequence. Recheck this boundary when upgrading the vendored driver.
- Diagnostics and cleanup: on failure, save screenshot, page source and error under the configured E2E artifact directory before cleanup. Clear the backend fixture, wait for a pending setting write when possible, then attempt the original KV write, readback, refresh, route recovery and final readback even if an earlier cleanup step fails. Aggregate cleanup errors and preserve the primary test error if both fail.
- Recovery coverage: a failure to read must expose Retry; a failed write must preserve the old backend value; an unsupported version from an event or initial read must block edits and preserve the exact stored value; a successful retry must converge in the current UI and storage; refresh must reload the persisted value.
