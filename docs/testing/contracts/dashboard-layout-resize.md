# Dashboard responsive layout resize contract

- Contract ID: `dashboard-layout-resize`.
- Boundary: the main Dashboard's real window-size and `ResizeObserver` path.
- Suite: `dashboard-main-layout.e2e.ts`, registered in the `main` suite and included by `hermetic`.
- Setup: snapshot the exact `dashboard-widgets` storage value and current window dimensions; write a deterministic fixture with one item in `4x5` and six widgets in `8x6`, then refresh the Dashboard so the fixture is loaded by the real storage hook.
- Operation: resize the real desktop window to a narrower width and wait until the single-widget `4x5` layout is visible; restore the original wide dimensions and wait for all six `8x6` widgets and both shortcut cards.
- Assertions: the viewport selects the expected layout at each settled size, and responsive projections do not overwrite the fixture. In `finally`, restore the original KV value and window dimensions, refresh the route and verify the exact stored value.
- Interaction guard: `DndGrid.onInteractionChange` reports grid drag/resize activity. A resize-selection timer that expires during an interaction remains pending and is applied after the interaction ends. The desktop spec does not synthesize a simultaneous drag-and-window-resize sequence.
- Coverage limit: this verifies settled selection through the desktop resize observer. It does not assert every intermediate animation frame or a precise 200 ms timing boundary.
- Failure evidence: before cleanup restores the window and fixture, the test records the failure phase, expected state, route, viewport, target widget bounds, privacy-safe persisted-storage summary, primary error, build identity (source commit plus actual E2E binary SHA-256), and sanitized `error`, `unhandledrejection`, and `console.error` events observed after the error listener is installed. Initial page-load and route-render errors that occur before listener installation are outside this capture's scope. Frontend events are sanitized inside the WebView before crossing the WebDriver boundary. WDIO logger masking is configured for common credential formats before its request layer logs response errors, and the project rules are merged with any pre-existing `WDIO_LOG_MASKING_PATTERNS`; Node-side WebDriver/cleanup exceptions and their nested causes are also sanitized before artifact or test output. Screenshot and page source use a unique run/spec/test/attempt path and remain raw captures of the isolated E2E runtime; do not export them from a manually shared runtime without reviewing their contents. WebDriver requests in the responsive test body, evidence capture, and cleanup temporarily use a 5-second transport timeout with retries disabled; the test's explicit 5/10-second state waits keep their separate deadlines. This aborts the client request, but cannot guarantee cancellation of a command already executing in the embedded driver. Frontend errors are copied before cleanup so later cleanup failures retain the same snapshot. The final JSON is written after cleanup with each cleanup outcome and every cleanup error. The kernel is not applicable to this layout-only contract.
- Evidence: the test proves UI convergence and storage preservation. It does not prove layout behavior for every preset or operating system; the registered Windows hermetic run is required for PR evidence.
