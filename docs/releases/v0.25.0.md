# Chimera v0.25.0 Release Plan

## Release objective

Chimera v0.25.0 is a runtime-correctness and ownership release.

The release is limited to:

- transactional Chimera Service runtime apply / rollback / recovery;
- authoritative Service revision, health, controller binding, typed errors, and quarantine state;
- stable epoch runtime config storage and identity-verified process ownership;
- Local / Service endpoint ownership and commit-first host handoff;
- deterministic runtime document materialization and Local-only lifecycle revision ownership;
- guarded Windows Service + TUN lifecycle E2E coverage;
- immutable, checksum-verified Chimera Service release dependency handling.

Unrelated UI features, dependency migrations, and architecture work not required to satisfy these guarantees are deferred to a later release.

### Windows Service / TUN system lifecycle

This is a hard release gate, not an optional smoke test.

The release branch must pass the destructive `system` suite on an elevated disposable Windows runner. The suite must verify:

- Service install / start / stop ownership;
- Local -> Service and Service -> Local handoff;
- TUN convergence;
- Service restart recovery;
- process / PID identity cleanup;
- no pre-existing unmanaged Service ownership;
- final cleanup.

The local development host is not accepted for this gate because it is currently non-elevated and already has a running Chimera Service. GitHub-hosted release runners are used instead.

## Service release integrity

Before the Chimera application can be packaged:

1. `Chimera_Service v1.10.0` must be a non-draft, non-prerelease stable release.
2. Every expected archive and SHA-256 asset must exist.
3. The `v1.10.0` tag must resolve to the exact submodule commit pinned by the application.
4. Sidecar archives are downloaded and SHA-256 verified before packaging.
5. The final release system E2E must run against the downloaded stable Service sidecar, not a locally rebuilt replacement.

## Release order

1. Push `release/v0.25.0-runtime`.
2. Push `release/v0.25.0` with its exact runtime submodule pin.
3. Require release-branch CI plus the automatic Windows destructive system lifecycle gate to pass.
4. Dispatch the runtime `Publish` workflow on the runtime release branch.
5. Verify the generated `v1.10.0` prerelease candidate and all expected assets.
6. Promote `v1.10.0` to stable only after the candidate source gate is green.
7. Run `node scripts/check-service-release.ts` from the application release branch; it must verify stable state, assets, and exact commit SHA.
8. Dispatch the application `[Entire] Build Release Version` workflow for `v0.25.0`.
9. The workflow must run the Windows system lifecycle again using the checksum-verified stable Service sidecar before any platform packages are built.
10. Publish application artifacts only if every build and updater job succeeds.

## Current blockers

- `Chimera_Service v1.10.0` does not yet exist as a stable release. This is expected until the runtime candidate is published and promoted.
- The local machine cannot be used as the destructive Windows release runner because it is not elevated and already has an active Chimera Service.

No application release tag should be created while either release dependency gate is unresolved.
