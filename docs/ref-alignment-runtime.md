The shared path and candidate flow maps to `ref/backend/tauri/src/client/runtime.rs::RuntimePaths`, `create_candidate`, and `promote_candidate`. Chimera keeps those paths and names: the runtime product is `<config>/runtime/clash-config.yaml`, while candidate files live under `<config>/runtime/.candidates`.

The production restart and recovery path follows the ref lifecycle workflow. `backend/tauri/src/setup.rs` constructs `CoreFacade::new_local_with_control`, which installs a `LocalRuntimeHost`. `CoreLifecycleWorkflow::{reconcile, submit_runtime}` and `runtime_recovery::verify_recovery_target` in ref map to Chimera's lifecycle workflow, `LocalRuntimeHost::reconcile_with_profile_source`, and `LocalRuntimeHost::restore_runtime_receipt`. Chimera checks the saved bytes and execution host, submits against an authoritative runtime revision, then verifies a fresh status against the confirmed submission before promoting the restored runtime product. Unlike ref, this confirmation is currently implemented in the local runtime host's restore path rather than a separate recovery-verification module.

Port selection follows ref's `CandidatePortBindings` and `SessionPortResolver::{resolve_candidate, invalidate}` contract. Candidate resolution is inert, and the resolver reads the confirmed binding from the same runtime lifecycle store that owns the apply receipt. A confirmed core apply makes that binding available even while its Profile transaction awaits confirmation, because it describes the runtime already serving traffic. An uncertain operation, failed restore, stop, or host change marks the binding unavailable while retaining the receipt for recovery. Ref's verifier also handles a stopped receipt as a target; Chimera currently rejects restoring a stopped receipt, consistent with its current workflow policy that prevents critical apply attempts while the core is stopped. Revisit that difference if the policy changes.

The `todo!()` branches in `backend/tauri/src/core/clash/core.rs` belong to the older manager-only compatibility path. The production setup constructs `CoreFacade::new_local_with_control`; `CoreFacade::new_local()` is now compiled only for tests and has no production call site. This old manager does not receive the typed `Profiles` snapshot required by the shared runtime builder, so implementing restart and recovery there would create a second configuration path. Keep those branches out of production use and retire the compatibility path when its remaining test/adapter callers are migrated. The separate `RuntimeTransactionSnapshot`, `capture_runtime_transaction`, and `restore_failed_apply` helpers are exercised by helper tests but have no active production caller; do not treat them as proof of production restart recovery.

The typed user settings file at `<config>/clash-config.yaml` is owned by `PathResolver::clash_config_path()` and the typed-config migrator. It must never be treated as a runtime-product backup. The legacy transaction helper records a missing runtime product as `None`; its rollback removes a failed new runtime product and leaves the typed settings file byte-for-byte unchanged. Production recovery instead restores the exact confirmed runtime receipt and leaves the typed settings file under its existing owner.

Recheck this difference when the manager-only compatibility path is removed or the reference changes its runtime transaction model. Keep the production receipt recovery aligned with the reference workflow and document only the smallest compatibility behavior needed by the supported legacy UI and agent boundaries.

## TUN auto-route ownership (2026-11-11, partial)

Guard and TUN ownership still share the existing `GuardOverrides` snapshot node; the finalizing stage still supplies stack and DNS defaults. There is no new UI control for `tun.auto-route` because the reference does not expose one. The pure config pipeline does not create a TUN device or change host routes, DNS, or system proxy.

## Plan and Inspect stage separation (2026-11-11)

Chimera now declares `GuardInputs`/`TunParams` ownership in
`backend/chimera-config/src/runtime/executor/plan.rs`, keeping Chimera-specific
resolved ports and `routing-mark` semantics. The current pure Executor records
`WhitelistFieldFilter`, `KeepUnmanaged`, `ManagedSettings`,
`TunKeepUnmanaged`, `TunManagedSettings`, then built-in transforms,
`FinalFieldFilter`, `Defaults`, and the final `Finalizing` node. The legacy
`GuardOverrides` tag is retained for deserializing older graphs. Guard and TUN
ownership are deliberately separate to preserve the intermediate insertion
order that built-in scripts observe. Generated Specta bindings and five
localized Inspect labels accompany the Rust tags.

The second filter still preserves Chimera Client's `mmdb` capability boundary;
TUN/DNS defaults stay *after* built-in transforms; the final node retains
include-all expansion and sorting. These stages expose internal config
transformations but do not imply runtime Core acceptance. Unset listener ports
retain current Chimera behavior rather than adopting the reference's removal
policy. The review-only `ref` checkout was `b37e18444e3df012fe8f548e7e0818ed8b4aa227`
while the parent repository's tracked `ref` gitlink remains
`59724e85c34abb6995c22d101c876cc06dc16576`; the existing ref
`backend/Cargo.lock` change was deliberately left untouched. Do not claim
full pinned-reference parity based on this partial stage alignment.

The corresponding unit tests assert final configuration content, stage order,
pre-builtin config insertion order, filtered keys, TUN/DNS/cache defaults, and
Inspect step identities. No live TUN, Service, DNS or desktop E2E test was run.
