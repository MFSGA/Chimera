- Difference and reason: Chimera retains its `CoreLifecycleClient` and `CoreFacade` boundary for local and Chimera Service execution. `ApplicationMutationParticipant<Profiles>` adapts typed Profile candidate commits to that boundary and restores the prior snapshot on rollback. Profile operations now use ref's `OperationId` identity. A typed, known-not-admitted `QueueFull` result may be deferred for `Save` commands and schedules a rebuild after source commit; all other runtime failures fail the Profile transaction closed. If rollback fails, the participant latches the cause and the next Profile mutation retries reconciliation to the last committed Profile snapshot when the core state is observable; an uncertain core outcome remains blocked for core-level recovery. Chimera's generated IPC file exposes direct `commands` but does not generate ref's `queries`/`mutations` descriptors, so `profile-bindings.ts` exports the corresponding typed Profile descriptors without editing generated output. Its `RemoteProfileImportMode::Direct` and global-transform mutations remain explicit Chimera extensions. The Profile participant still does not use ref's tracked application workflow/TCC lifecycle or full recovery receipts, so transaction architecture remains partially aligned. In the transform path, `JSRunner` now uses ref's OXC `FunctionVisitor`/`wrap_script_if_not_esm` strategy and accepts both supported script forms; it keeps QuickJS for execution and enforces Chimera's memory budget through a capped allocator because `Runtime::set_memory_limit` is a no-op with a custom allocator. Parsing the original, untrimmed source also avoids the span offset error that would result from inserting into a source with leading whitespace. These engine and memory-isolation choices are Chimera runtime adapters, not a change to Profile's public transform contract.
